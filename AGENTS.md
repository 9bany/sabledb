## Repository navigation
[tag:navigation]
This repository is a Rust workspace centered on `libsabledb`. Start there when you need the shared command, storage, replication, or server APIs.

Primary directories of interest:
- `crates/libsabledb`: core library and the main code surface.
- `crates/sabledb`: server binary.
- `crates/sdb-cli`: interactive/client binary.
- `crates/sdb-admin`: admin binary.
- `docs/`: high-level repository documentation.
- `submodules/benchmark/`: benchmark workspace.
- `support/compatibility_check/`: compatibility tooling and command metadata support.

## Major subsystems
[tag:subsystems]
- **Commands**: command families are split by data type and execution role.
- **Storage**: storage is abstracted behind a common adapter with RocksDB-backed persistence.
- **Replication**: node communication, cluster state, and storage updates live here.
- **Server runtime**: server startup, worker management, cron behavior, and client state.
- **Metadata**: typed value models and bookkeeping helpers.
- **Utilities**: RESP helpers, parsing, pattern matching, timing, and low-level helpers.

## Key entry points
[tag:entry-points]
- `crates/sabledb/src/main.rs` — server bootstrap and listener loop.
- `crates/libsabledb/src/lib.rs` — public re-exports and macro helpers.
- `crates/sdb-cli/src/main.rs` — command-line client flow.
- `crates/sdb-admin/src/main.rs` — admin subcommand dispatch.
- `crates/libsabledb/src/server/server_options.rs` — config loading and CLI overrides.

## Repo-specific notes
[tag:repo-notes]
- Config is INI-based; `conf.ini` and `server.ini` show the runtime shape.
- The server accepts a config file as the first trailing argument, with CLI flags overriding file values.
- The CLI supports both interactive and file/inline batch execution.
- There is a GitHub Actions workflow in `.github/workflows/rust.yml` that builds, lints, and tests the workspace.
- Do not spend time in `target/` when navigating source behavior; it is build output.

### Adding a new complex/custom data type

Follow the `List` type as the reference pattern (`crates/libsabledb/src/metadata/list_metadata.rs`,
`crates/libsabledb/src/storage/list_db.rs`); `AuditLog` (`metadata/audit_metadata.rs`,
`storage/audit_db.rs`, `commands/audit_commands.rs`) is a second, simpler worked example (append-only,
no linked-list bookkeeping needed).

1. Add a `ValueType` variant and a `KeyType` variant (for the type's sub-item records) in
   `metadata/encoding.rs`. Add `is_x()`/`set_x()` to `CommonValueMetadata`
   (`metadata/value_metadata.rs`).
2. Add a `<Type>ValueMetadata` struct in `metadata/<type>_metadata.rs` (the container record,
   stored under the type's primary key) and register it in `metadata/mod.rs`.
3. Add a `<Type>Db` struct in `storage/<type>_db.rs` (mirrors `ListDb`: wraps `DbWriteCache`,
   exposes the type's operations). On first-write/creation, write a `Bookkeeping` record
   (`metadata::Bookkeeping::new(...).with_uid(...).with_value_type(ValueType::X)`) so orphaned
   sub-items (left behind if the primary key is later deleted or overwritten by an unrelated type)
   can be reclaimed. Register the module in `storage/mod.rs`.
4. To make the periodic Evictor (`server/cron_thread.rs`, `Cron::evict`) actually reclaim those
   orphans, add `(ValueType::X, vec![KeyType::XItem, ...])` to its `prefix_arr` list -- this is a
   separate, easy-to-forget step from writing the Bookkeeping record itself.
5. Replication needs no type-specific code: everything written through `DbWriteCache`/
   `StorageAdapter` replicates automatically as raw Put/Del records streamed from the primary's
   RocksDB WAL (`StorageAdapter::storage_updates_since` / `apply_storage_updates`,
   `replication/client_replication_loop.rs`). When testing this, open stores with the WAL enabled
   (`StorageOpenParams::set_wal_disabled(false)`) -- `crate::tests::open_store()` disables the WAL
   for speed, which silently makes `storage_updates_since` return nothing.
6. If exposing the type via a RESP command, register it in `commands/commander.rs`'s
   `ValkeyCommandName` enum + command table (arity, `.write()`/`.read_only()`, key positions),
   dispatch it in `server/client.rs`'s big match, and export the `*Commands` handler from
   `commands/mod.rs` + `lib.rs`. **Gotcha:** `CommandMetadata::to_resp_v2()` (used by `COMMAND` /
   `COMMAND DOCS`) derives a command's self-reported name via
   `ValkeyCommandName::command_name()`, which defaults to the lowercased `Debug` name of the enum
   variant. That must match the string key you registered in the command table exactly (e.g.
   `Lpush` <-> `"lpush"`) or `COMMAND`/`COMMAND DOCS` output will silently omit/misname it. A
   dotted command name (e.g. `AUDIT.APPEND`, enum variant `AuditAppend`) can't satisfy that via
   `Debug` alone -- add an explicit override arm in `command_name()` instead of trying to encode
   dots into the enum variant name.

### Known-fixed gotchas

- `RespResponseParserV2::parse_response` (`utils/resp_response_parser_v2.rs`) used to mishandle an
  empty (as opposed to null) RESP bulk string (`$0\r\n\r\n` vs `$-1\r\n`): it returned the right
  object but failed to consume the trailing `\r\n`, desyncing parsing of anything that followed in
  the same buffer/array. This is fixed; if a test parsing a RESP response mysteriously fails with
  "unexpected token found `13`" (`\r`'s byte value), suspect a *new* instance of this class of bug
  rather than this one.
